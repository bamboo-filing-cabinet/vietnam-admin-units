# District granular (year-by-year) crosswalk probe

Written 2026-07-13. Follow-up to `2026-07-13.01`, which flagged (Next steps #3)
the open question: is the single 2002→2025 district crosswalk enough, or are
intermediate/finer-grained pulls needed? **Answer: finer-grained pulls are needed
and they work well.** This journal records the validation.

## Why the flat 2002→2025 export is insufficient

Parsing the cached `Đối chiếu … cấp Huyện … 01_01_2002 và 30_06_2025.xls`
(713 rows) shows the `Ghi Chú` column is pure boilerplate:

- `"Chuyển đổi mã đơn vị hành chính 2002 - 2004"` ×626, blank ×87 — **no
  composition prose at all.**

It is a *flattened* old→new code map over 23 years: 609 survivors mapped
(5-digit→3-digit), 87 "new" (blank old side), 17 "dissolved" (blank new side).
Mid-window **lineage** is lost — e.g. Huyện Từ Liêm split (2013) into Nam + Bắc Từ
Liêm shows only as `Từ Liêm(10121) → Nam Từ Liêm(019)`; **Bắc Từ Liêm(021)
appears as "new" with no link back**, and the 17 dissolved districts carry **no
merge target**. (The compare-side effective *dates* are preserved even in the flat
export — Từ Liêm's successor correctly shows 2013-12-28 — so it's the lineage
structure and the `Ghi Chú` prose that the flat window destroys, not the dates.)

## Granular windows fix this — validated on 2013→2014

Ran the Đối Chiếu page (`Doi_Chieu_Moi.aspx`) at **Cấp=Huyện, Ngày gốc
01/01/2013, Ngày đối chiếu 01/01/2014**, scraping the rendered grid
(`tr.dxgvDataRow`, 13 columns) directly from the DOM.

Result: **711 district rows total, exactly 17 changed, and every changed row has a
2013 effective date.** The narrow window **cleanly isolates that year's events**
with *precise* effective dates:

| base | successor | eff. date | note |
| --- | --- | --- | --- |
| Huyện Từ Liêm (019) | Quận Nam Từ Liêm (019) | **28/12/2013** | split primary (code-inheriting) |
| — (new) | Quận Bắc Từ Liêm (021) | 28/12/2013 | split sibling — same decree `132/NQ-CP` |
| Thị xã Lai Châu (105) | Thành phố Lai Châu (105) | 28/12/2013 | type upgrade, with prose |
| — (new) | Huyện Vân Hồ (128) | 11/06/2013 | new (from Mộc Châu) |
| — (new) | Thị xã Hoàng Mai (432) | 04/04/2013 | new |
| — (new) | Huyện Quảng Trạch (454) | 21/12/2013 | new (Quảng Trạch/Ba Đồn split) |

(An earlier read that showed 2020-dated rows in this window was **stale DOM
contamination** from a prior Xã query, not a real result — a fresh query returns
only 2013 events. Always re-query into a clean page.)

### Key finding: `Ghi Chú` prose survives in narrow windows

Contrary to the flat export, narrow windows that **stay within one code-era** keep
real composition prose in `Ghi Chú`, e.g.:

- `"thành lập thị xã Lai Châu trên cơ sở … thị trấn Phong Thổ, xã Nậm Loỏng, xã
  Tam Đường, …"`
- `"Nhập toàn bộ … của huyện Thông Nông vào huyện Hà Quảng"`
- `"nhập vào huyện Quảng Uyên, thành lập huyện Quảng Hòa"`
- `"Thay đổi loại hình"` (type change)

The flat 2002→2025 export overwrites all of it with the `"Chuyển đổi mã 2002-2004"`
boilerplate **because that window crosses the 2004 code switch**. Prose is present
for some events, absent for others (the Từ Liêm split rows were blank) — so
lineage still needs the Phase-1 **combination** strategy: decree + effective-date
grouping (split/merge siblings share a decree) + `Ghi Chú` prose where present +
name/province matching for the residue.

## Recommended methodology

- **Sweep yearly windows** `01/01/YYYY → 01/01/(YYYY+1)` for `YYYY = 2004…2024`
  (~21 windows), each within the 3-digit code-era → clean per-year change sets
  with true effective dates.
- **Handle 2002→2004 as a separate boundary pull** (the known 5-digit→3-digit
  code remap; no event prose there — journal `.15`, `.01`).
- Anchor lineage on **decree + effective date**; group split/merge siblings that
  share them; enrich with `Ghi Chú` prose; matched against per-window snapshots.

## Extraction mechanism — how to pull each window

The Đối Chiếu page is a **DevExpress WebForms** app. Findings for automation:

- **Cấp** value → hidden field `ctl00_PlaceHolderMain_cmbCap_VI` (`2` = Huyện;
  empty in served HTML, populated client-side).
- **Dates** → hidden `_Raw` fields in **epoch milliseconds**
  (`ctl00_PlaceHolderMain_txtNgay_Raw`, `…_txtNgayDC_Raw`), *not* the dd/mm/yyyy
  text inputs. Server reads `_Raw`.
- **Excel button** (`ctl00_PlaceHolderMain_cmdExcel`) is an **ASPxButton** fired
  via `__EVENTTARGET`, and `SetVisible(true)` **only after a query runs** — so its
  postback target isn't in `__EVENTVALIDATION` on a cold load. Requires a
  "Thực Hiện" (`ASPxButton1`) round-trip first.
- A plain `requests` 2-step replay (Thực Hiện → Excel) still returned grid HTML,
  not the `.xls` — the combo/grid appear to use **AJAX callbacks**, awkward to
  hand-roll.

**A scripted export IS possible** (the Excel response is a normal server-side file
POST — no browser save-dialog needed when scripted). Recommended paths, in order:

1. **Headless browser (Playwright):** drive the page, click Excel, capture the
   download to a dir → verbatim `.xls` per window → cache + manifest + parse.
   Best provenance; handles VIEWSTATE/callbacks natively.
2. **DOM-scrape** (proven working here): extract `tr.dxgvDataRow` per window.
   Simpler, no download, but yields structured rows only (no verbatim `.xls`).
3. Hand-rolled `requests`/callback replay — brittle; not recommended.

Operational caveat (from `.01`): the user's Chrome is set to *"ask where to save
each file"*, so interactive Excel clicks stall on the save dialog. Scripted paths
(1 with a configured download dir, or 2) avoid this.

## Limits of the yearly-window approach (found 2026-07-13)

Two boundaries on what this sweep can see:

1. **Đối Chiếu cannot resolve pre-2004 events — there is a hard event floor at the
   2004 code change.** When the *base* date is in the 5-digit era, the tool ignores
   the compare date and always returns the same 2002→2004 code-conversion mapping
   (626 rows, 0 changes, 100% `"Chuyển đổi mã 2002-2004"` boilerplate). Verified:
   `2002→2003`, `2003→2004`, and `2002→2004` exports are **byte-identical**
   (sha `0a1e516…`). Events only appear once the compare date is post-2004 (that's
   why `2004→2005` works). So 2002–mid-2004 district *events* are a black box here;
   the flat 2002→2004 file is kept only as the code-remap table (5-digit→3-digit).
   Pre-2004 change history would need Lịch Sử / Nghị định / external sources.

2. **A yearly (snapshot-diff) window collapses same-year churn on the *same* unit.**
   Any two point-in-time snapshots show only the *net* change between them:
   - date precision is **not** lost — each captured change carries its true
     day-precise effective date (e.g. the 2007→2008 window captured 21 changes
     across 14 distinct dates over 7 months), and *different* units changing in the
     same year are all captured individually;
   - but if the **same unit** changes twice in one year (e.g. rename then
     type-upgrade), only the year-end state shows; and a unit **created and
     dissolved within one year** is net-invisible (never appears in any window).

   For districts the risk is low — events are decree-driven and sparse (0–61/year),
   no VN district was created-and-abolished within a single year in 2002–2025, and
   same-district-twice-in-a-year is rare. But it is a real structural limit, and it
   becomes first-class for **Phase 3 wards** (the 2019–24 waves). Mitigation (the
   `DESIGN.md` hybrid): drive windows by the **event list** — the Nghị định (decree)
   page / Lịch Sử change-log enumerate events with dates — and/or cross-check the
   yearly captures against that decree list to confirm no same-unit-twice or
   ephemeral units before finalizing lineage. Finer (monthly/quarterly) windows are
   mostly wasted pulls; event-driven is the right tool.

## Implemented (2026-07-13)

- **Fetcher** `vn_admin_units.crosswalk_fetch` (Playwright, `ingest` dep group):
  drives the DevExpress page (Cấp=Huyện via `cmbCap` autopostback → `SetDate` on
  the ASPxDateEdit controls → `cmdThucHien` → capture the `cmdExcel` download) and
  caches the verbatim `.xls` per window with a manifest entry. Reuses one page
  across windows (Cấp stays Huyện). `--sweep START END` or `--window BASE COMPARE`.
- **Parser** `crosswalk.read_district_crosswalk` (13 positional cols; Excel-serial
  → ISO dates). TDD'd in `tests/test_district_crosswalk.py` (4 tests).
- **Sweep complete:** 23 windows cached — yearly 2004→2024 (21) + the 2002→2004
  code boundary + the 2025-01→2025-06 pre-abolition tail. Flat 2002→2025 export
  also added to the manifest.

Change timeline recovered (changed rows per yearly window): 2004→05 **61** (34 new,
post-code-change wave), 2007→08 21, 2009→10 25, 2013→14 17 (Từ Liêm split),
2019→20 9 (2 dissolved), 2020→21 19 (6 dissolved, Cao Bằng), 2024→25 26 (11
dissolved, pre-abolition). Quiet years (2014→15, 2016→17) show 0 — confirming the
windows isolate real events.
