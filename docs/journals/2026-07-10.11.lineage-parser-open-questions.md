# Lineage parser — open questions & risks (from taxonomy probing)

Written 2026-07-10. Probed the `Ghi Chú` against the change taxonomy (`.10`) to
find what's still unresolved for the lineage build. Surfaced one clean result,
one real problem, and several design decisions.

## Resolved

**Verb classifier is ~clean.** Over the 3,321 base=new ward rows: `hợp nhất`
3160, `đổi tên` 1833, `giữ nguyên` 128, `một phần/1 phần` 372, `bỏ cấp huyện`
3320; `sáp nhập` 2, `chia` 0, `thành lập` 14. Only **12 rows** lack a core verb —
all **typos** (`Họp nhất`, `Hơp nhất`, `Sắp xếptoàn bộ`). So event-type
classification from verbs is viable at ~99.6%, with fuzzy/normalized matching.
Note `hợp nhất` (consolidate → new, M2) dominates over `sáp nhập` (absorb, M1) —
reinforcing the new-entity model (`.08`, `.10`).

**Splits are real and common — lineage is many-to-MANY.** An old unit's
territory frequently goes to several new units (S1 split), not just many-old →
one-new (M2). Province-scoped, **401** old `(province, name)` feed >1 new ward;
clear real cases: Hà Nội **Đại Mỗ → 5** new wards; **Điện Biên → 4**. **372** new
wards receive ≥1 `một phần` partial contribution. So the model and the WD
encoding must support **one-old → many-new with proportions**, not only merges.
`một phần` + `P518`/`P1107` is core, not a corner case.

## The real problem: Ghi Chú references are name-only and ambiguous

`Ghi Chú` names constituents as bare `phường X` / `xã Y` — **no codes**. And VN
ward names are heavily duplicated: name-only matching gave 707 "splits"
nationally that collapse to 401 province-scoped, the difference being pure
name collisions (`Quang Trung` appears in ~22 provinces). Even *within* a
province, the pre-reform district tier allowed duplicate commune names across
districts, so `(province, name)` is still not guaranteed unique.

**Consequence:** turning a parsed `Ghi Chú` constituent into a specific
predecessor **code/QID** requires **disambiguation by context** — the new unit's
province + the (abolished) old district + the pre-reform snapshot — and a
residue will need manual resolution. This is the hard core of the ward lineage
build.

**Critical caveat for phasing:** **province-first does NOT de-risk this.**
Province names are unique, so the province `Ghi Chú` parse is trivial and clean —
it validates the *pipeline shape* (parse → edges → qualifiers → WD batch) but not
the *name→code disambiguation* that dominates the ward tier. Plan a dedicated
ward-disambiguation step (and its own validation) in Phase 1b; don't assume a
green province run means wards are solved.

## Approaches to the disambiguation problem (to decide)

1. **Context join against the pre-reform snapshot.** For each new ward, resolve
   each named constituent to the old ward of that name whose old district sits in
   the same pre-reform province region. Uses SOAP base=old snapshot (has codes +
   old district). Ambiguity remains where a name repeats across districts of the
   same old province.
2. **Cross-check with the structured primary link.** The base=old export's `Xã DC`
   gives the primary (code-level, unambiguous) for 3,321 old wards; use it to
   anchor, and resolve only the absorbed/partial constituents from prose.
3. **Third-party crosswalk cross-validation.** `tranngocminhhieu/vietnamadminunits`
   has a 63→34 old↔new mapping with an `isDefaultNewWard` split flag — use to
   validate/fill.
4. **Accept a manual-resolution residue** with a curation file for the
   unresolvable names.

Likely a combination: (2) anchors primaries, (1) resolves the rest, (3)
validates, (4) mops up.

## Remaining design decisions (not probes)

- **Which reforms in scope for Goal B?** 2025 only, or also 2008 (Hà Tây→Hà Nội)
  and 2004 splits — and do we **chain** multi-hop lineage across all of them
  (trace a place through 2004→2008→2025)?
- **Predecessor reconciliation scope.** New-entity + lineage means we need QIDs
  for **all** predecessors (the ~10k old ward items), not just the 3,321 new
  units. Sizes the reconciliation work.
- **WD qualifier validity.** `P1365`/`P7888` allowed-qualifier + value-type
  constraints for the partial/primary/date qualifiers — still unverified (WDQS
  was under outage). Blocks batch design.
- **Observation cadence.** Store SAME-entity attribute history per snapshot date,
  or only per detected change event? Affects the `observations` schema size.
- **Data-quality normalization.** Ghi Chú has typos, stray newlines, missing
  spaces, and a đặc-khu count wobble (12 vs 13) — needs a cleaning pass with a
  logged correction list (never silent).

## Net

The parser's easy 90% (verb classification, primary links, province tier) is
confirmed feasible; the hard 10% (name→code disambiguation of merge/split
constituents at ward scale) is the real work and is **invisible at province
level**. Build province-first for the pipeline shape, but budget explicitly for
ward disambiguation as its own sub-project with its own validation.
