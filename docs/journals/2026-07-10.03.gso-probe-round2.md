# GSO probe round 2 — bulk fetch, types, ward-code reuse, data quality, Wikidata

Written 2026-07-10. Continues `2026-07-10.02` (SOAP contract + Group A identity
/dating). This round knocks down bulk-fetch feasibility, the type enumeration,
ward-level code reuse, and the Wikidata reconciliation question — and turns up a
source data error.

## Bulk fetch: one call per tier per date (empty `Tinh`)

`DanhMucPhuongXa(DenNgay, Tinh="", QuanHuyen="")` returns the **entire national
ward tier in a single call** — 3,321 wards, ~922 KB, for the current date.
`DanhMucQuanHuyen(DenNgay, Tinh="")` likewise returns all districts (696 rows
for a pre-reform date). So the historical crawl is trivial, not a
province-by-province fan-out:

- Per snapshot date: `DanhMucTinh(d)` + `DanhMucPhuongXa(d, Tinh="")`
  (+ `DanhMucQuanHuyen(d, Tinh="")` for pre-reform dates).
- **~2–3 calls per date × a handful of boundary dates = the whole history.**

Resolves the "bulk-fetch strategy" open question: no throttling gymnastics
needed; just commit the raw per-date dumps as the reproducible cache.

## Type (`LoaiHinh`) enumeration + formats

Current national dump:

  `Đặc khu` ("special zone") is a **new post-reform ward-tier type** (island /

- **Province tier `LoaiHinh`:** `Thành phố Trung ương` (centrally-governed

- **Empty fields:** `Vung`, `TThi_NThon`, `KhuVuc` come back **empty** in the
  national dump → **drop for v1** (answers the ward-field-semantics question).

## Ward-code reuse across the reform — confirmed and severe

The A2 residual, now tested. Hà Nội (`Tinh=01`, a province that did **not**
merge), wards pre-reform (`01/06/2025`) vs current:

- 526 wards → 126 wards; **126 codes kept, 0 new, 400 retired.**
- **Of the 126 kept codes, 104 now point at a *different* ward name** — e.g.
  `09676` Xã Sơn Đà → Xã Bất Bạt; `00235` Phường Thịnh Quang → Phường Đống Đa;
  `00103` Phường Xuân La → Phường Tây Hồ.

So GSO recycles ward codes wholesale: `MaPhuongXa` is a **slot, not an
identity**. This is worse than the province-level A1 (104/126 reassigned). A
naive `MaPhuongXa` join across the reform would be catastrophically wrong.
Confirms: **ward identity must be keyed `(code, era)` on the `local_id` spine**,
same as provinces.

## Province timeline — now fully mapped

Mid-span (2008→2025) province set is stable at 63 with a single rename:
`46` Tỉnh Thừa Thiên Huế → Thành phố Huế (Huế's upgrade to centrally-governed
city, showing by 2025). No other renames 2008–2020. Full first-level timeline:

`61 (2002 epoch) → 64 (2004-06-30) → 63 (2008-08-01) → [46 Huế→city] → 34 (2025-07-01) → [75 Đồng Nai→city, cities 6→7, 2026-04-30]`

Note the last event keeps the count at 34 but is a `LoaiHinh` change — so the
timeline must track type/name changes, not just counts.

## Data quality: 7 centrally-governed cities is CORRECT (a corrected mis-call)

The current province dump reports **7** `Thành phố Trung ương`. My first read
called the 7th — `75` "Thành phố Đồng Nai" — a GSO mislabeling error, since
Đồng Nai had been a province. **That was wrong.** Đồng Nai genuinely became a
centrally-governed city on **2026-04-30**, corroborated by
[Tuổi Trẻ, 2026-04-25](https://tuoitre.vn/dong-nai-len-thanh-pho-ky-vong-dot-pha-20260425082132067.htm).

Verified against the service: code `75` reads `Tỉnh Đồng Nai` at `01/08/2025`
and `01/01/2026`, and flips to `Thành phố Đồng Nai` / `Thành phố Trung ương`
bisected to **2026-04-30** — matching the news to within days. So the 7 cities
are: Hà Nội, Hải Phòng, Huế, Đà Nẵng, HCMC, Cần Thơ, **and Đồng Nai**.

**Lesson (the real one):** the source was right; my *external assumption* was
stale. Verify a suspected source error against (a) the service's own dated
history and (b) an external source *before* declaring it an error — I nearly
recorded a false "correction" that would have propagated the wrong way upstream.
A validation layer is still worthwhile, but it must flag anomalies for review,
not auto-"fix" them. It also shows `DenNgay` captures **recent** changes to the
day (the 2026-04-30 upgrade), consistent with the merger dates in `.02`.

## Wikidata reconciliation — no code join available

Three independent checks agree there is **no Wikidata property for the GSO
`mã ĐVHC`** at any tier:

- Property search for "Vietnam" → only `P8500` (middle name), `P5625`
  (Vietnamese reading), `P13944` (company ID). No admin/GSO code property.
- Ward item `Q10838761` (Âu Lâu): claims are `P31` `Q2389082` (**"commune of
  Vietnam"**), `P17`, `P131` `Q36349` (**stale — old Yên Bái**), `P625`,
  `P2671` (Google KG ID). No numeric admin code.
- Province item `Q36446` (Lào Cai): only province-scoped external IDs —
  `P300` ISO 3166-2 (`VN-02`), `P901` FIPS 10-4, `P473` local dialing code
  (`020` ended 2017 → `214`). **None is a GSO code, none reaches district/ward,
  and all go stale on merger.** Crucially it has **no `P571`/`P576`/`P7888`** —
  the temporal/lineage scaffolding is exactly our model's gap to fill.

Consequences:

1. **Reconcile by `name-fold + parent-at-time + type + coordinates`**, not by a
   code join — no code property exists to join on.
2. **`P31` mapping is not 1:1:** `Xã` → commune (`Q2389082`), `Phường` → ward
   (separate QID, TBD), `Đặc khu` → special zone (QID TBD). Existing items also
   carry **stale `P31`/`P131`** (Âu Lâu still "commune" + old Yên Bái), matching
   what the `vietnam-elections-wikidata` lao-cai reference file documented.
3. **Upstream opportunity:** propose a Wikidata property for the GSO
   `mã đơn vị hành chính` so future reconciliation has a stable code join, and
   backfill `P571`/`P576`/`P7888` from our lineage graph.
