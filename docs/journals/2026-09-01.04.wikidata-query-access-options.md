# Wikidata query and data-access options

Date: 2026-09-01

Wikidata exposes several access paths that are useful for genuinely different
tasks. In particular, Wiki Replicas should not be treated as a relational copy
of the Wikidata knowledge graph.

## SPARQL: Wikidata Query Service

[Wikidata Query Service](https://query.wikidata.org/) remains the default
SPARQL endpoint.

The full graph was split into a **main** graph and a **scholarly** graph on
2025-05-09, with the split finalized in January 2026. The standard endpoint now
serves the main graph. Queries that need data from both graphs require
federation; the former `query-legacy-full.wikidata.org` endpoint is no longer
available.

This split does not affect the repository's National Assembly member and
administrative-unit queries because those subjects are in the main graph.

## QLever

[QLever's public Wikidata endpoint](https://qlever.dev/wikidata) is the likely
source of references to a faster alternative SPARQL service. It uses a
different query engine from the Blazegraph engine behind the official Wikidata
Query Service.

Benchmarks comparing QLever with Blazegraph, MillenniumDB, and Virtuoso found
QLever fastest and Blazegraph significantly slower. Both the QLever and
official endpoints serve Wikidata and track live edits, so QLever can replace
the official service for many read queries.

The Toolforge tool **To QLever** converts a WDQS query, or a
`query.wikidata.org` link, into a QLever-compatible query. The main migration
issues are Blazegraph-specific features such as `SERVICE wikibase:label`.

## Wiki Replicas

Wiki Replicas are MariaDB replicas of the **MediaWiki database**, not of the
Wikidata knowledge graph. From Toolforge, the access pattern is:

```sh
ssh login.toolforge.org
sql wikidatawiki
```

This exposes `wikidatawiki_p`. It is useful for querying:

- pages and revisions;
- sitelinks;
- change tags; and
- the Wikibase term store, including labels, descriptions, and aliases.

It does **not** expose statements as queryable relational columns. Claims are
stored as serialized JSON in blob storage outside the replica's useful SQL
surface. Wiki Replicas are therefore well suited to questions such as “which
items did user X edit after date Y?” or “which items have a Vietnamese
Wikipedia sitelink?”, but not “which people were members of the 15th National
Assembly?”.

Cross-database joins are also no longer available, so a query cannot directly
join `wikidatawiki` to `viwiki` in one SQL statement.

## Action API

The Wikibase Action API's `wbgetentities` action is the best fit for retrieving
the complete entity JSON for a small set of known QIDs. It is generally faster
than SPARQL for that access pattern and is the underlying path used by
Pywikibot.

## Dumps and local query engines

The Wikidata JSON dumps can be loaded into a local QLever or qEndpoint instance
when a reproducible snapshot is required. For this provenance-first project, a
pinned dump date can be more defensible than a live endpoint whose results may
change between runs.

## Practical recommendation for this repository

- Prefer QLever for read-heavy SPARQL queries when the query does not depend on
  Blazegraph-only syntax.
- Retain the official Wikidata Query Service as a compatibility fallback.
- Use `wbgetentities` for small batches of known QIDs.
- Keep Pywikibot for reviewed writes.
- Do not use Wiki Replicas for statement or claim queries.
- Consider a dated dump plus a local query engine when an input must be pinned
  for reproducibility.

The immediate workflow improvement is therefore to route ordinary read queries
through QLever while leaving the existing reviewed Pywikibot write path intact.
