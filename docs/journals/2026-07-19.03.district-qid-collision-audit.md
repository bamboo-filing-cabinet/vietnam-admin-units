# District QID collisions — full audit of shared QIDs (dig-in)

Written during the Phase-2 pre-upload pass (Wikidata batch dates are 2026-07-20 UTC). Follows the
2-collision fix in [[2026-07-19.01]]; triggered by the maintainer asking to re-check *all* duplicate
QIDs after the first fix. **Finding: my earlier "9 duplicate QIDs, 2 collisions, 9 legitimate
continuity" was wrong.** On inspection **8 of 9 are collisions** (two distinct units matched to one
WD item); only **1 is genuine continuity** (Đạ Huoai).

## Why the audit missed them
`audit_district_qids`'s distinctness check (added 2026-07-20) compared **folded** names, and
`fold_district_name` strips the tier prefix — so "Thành phố Cao Lãnh" and "Huyện Cao Lãnh" fold to
the same key and read as continuity. A province routinely has *both* a city and a rural district of
the same name; a 2013/2015 split produces a thị xã **and** a huyện. Name-fold can't tell them apart.
**Fix:** the distinctness check must key on the row identity (code + tier), not the folded name — flag
ANY QID shared by rows that aren't the same unit. (To land with the fixes below.)

## Method
For each of the 9 shared QIDs: (1) `wbgetentities` the shared item → its real label/P31/aliases;
(2) `wbsearchentities` the *wrongly-attached* counterpart's name → does its own item exist?;
(3) verify any candidate's P31 (tier) + P131 (province) against our row before proposing. All spaced
≥5s (Wikidata 429s bursts — see memory).

## Impact if shipped unfixed
- Coexisting pairs (Cao Lãnh, Hồng Ngự, Cai Lậy, Kỳ Anh, Duyên Hải, Long Mỹ): both rows pile
  P131+P576 onto one item (mostly dedup'd) — but the counterpart's real WD item gets nothing, and
  where a row has its own `valid_from` you get **two conflicting P571** on one item.
- Succession pairs (Thủ Đức merge 2021, Ayun Pa split 2007): the shared QID makes the emitter **skip
  P576 + P1366/P1365** (`pre.qid==post.qid` → "edited in place") — the abolition/succession is lost.

## Independent geo cross-check (2026-07-20) — ✅ clean, 0 wrong-place matches

All prior checks are name/tier/province-derived, so they can't catch a match to a same-tier,
same-province, plausibly-named but WRONG item. Ran a one-shot geographic cross-check using an
independent signal — Wikidata coordinates (P625), which cover **708/717 (99%)** of the mapped items:

- Pulled P625 for all mapped QIDs; grouped by claimed parent province.
- **k-nearest-neighbour province vote** (K=8): for each district, do its 8 geographically nearest
  district-items belong to its claimed province? Flag only when **0** of the 8 do (a real
  wrong-place signal; robust to province shape/density, unlike a centroid-distance test which
  produced 108 border/island false positives and even flagged known-correct matches).
- Result: **3 flagged, all explicable and correctly matched** — Côn Đảo (offshore island of
  Bà Rịa-Vũng Tàu, nearest the Sóc Trăng coast), Đông Triều (Quảng Ninh's town on the Hải Dương
  border), Bến Cát (Bình Dương city beside dense HCMC districts). **No district is matched to an
  item in the wrong place.**

This is the confidence pass for the residual class the name-based checks miss; it corroborates the
~700 auto-matched rows. (One-shot analysis, not committed as tooling — rerun from
`data/raw`/WD if needed.)

## Note
These are all auto-`matched` (bulk-reconcile) rows, same root cause as Thanh Sơn/Thanh Khê
([[2026-07-19.01]]) — name-based matching collapsing same-named distinct units. The label-over-alias
+ tier-check fixes already landed help future runs, but the audit distinctness (step 4) is what
actually catches these; without it they were invisible.
