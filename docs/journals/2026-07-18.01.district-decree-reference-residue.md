## What was done

Two search passes over the changed-row decree codes captured from the 23 cached
district Đối Chiếu windows (`data/raw/crosswalk/district_20*.xls`). Each code was
disambiguated by its **effective date + province** (bare CP-era codes carry no
year in the crosswalk cell), and every hit was verified against the landing
document, not just a snippet.

- **Pass 1 — thuvienphapluat.vn.** WebSearch by reconstructed `<code>/<year>` +
  title + province. **+53** `van-ban` URLs, **+5** typo-variant keys (a garbled
  crosswalk cell pointing at the same doc as an already-resolved code, e.g.
  `135/206/NĐ-CP`→`135/2006`, `829/UBTVQH14`→`829/NQ-UBTVQH14`).
- **Pass 2 — hard tail, authoritative-gov fallback** (= the README's open-decision
  option **(a)**). Identity was already known; agents hunted the exact page and,
  when thuvienphapluat wouldn't surface, accepted a verified
  `chinhphu.vn` / `congbao.chinhphu.vn` / `luatvietnam.vn` / `dangcongsan.vn` URL.
  **+15** high-confidence gov URLs.

**`data/decree-urls.json`: 63 → 136** (two automated passes), **then → 151** after
the maintainer browser-resolved all 15 of Residue A (2026-07-18). Suite 91 passed.

Mechanism note (still true, journal `2026-07-13.02`): the crosswalk decree column
is a *later* "last-touching" instrument, and the Nghị định *list* titles name the
**province**, not the district — so reference URLs cannot be scraped, they are
curated here per code.

## ▶ Residue D — `621/TCTK-PPCĐ`: exclude as a code-only re-code (recommended)

**What it is (verified against the crosswalk):** a single Tổng cục Thống kê công văn
`Số: 621/TCTK-PPCĐ ngày 31/08/2015`. It appears on **66 rows, all dated 2015-08-31**,
every one with ghi_chu **"Điều chỉnh mã địa bàn hành chính"** — it *only* re-assigns the
GSO `mã ĐVHC` code. The units it touches (thị xã Kỳ Anh, Duyên Hải, Long Mỹ…) were
*created* earlier in 2015 by real UBTVQH13 resolutions (903 etc., already referenced);
this letter just adjusted their statistical codes months later. It is **not** a legal
instrument that changes identity/boundary/type.

**Recommendation: exclude it from event discovery + the reference gate** (don't resolve a URL).
- **Why (pros):** a GSO code change is captured by the entity's chronological `gso_codes`
  list — it emits *no* `P571/P576/P131/P31` statement, so there's no statement for an
  `S854` reference to sit on. The real identity events are already referenced by the 2015
  resolutions; no provenance is lost. And an internal statistical công văn isn't published
  in any legal DB, so requiring a URL would block the gate permanently. It's the same class
  as the 2004→2005 recode the assembly already treats as code-only (alias source).
- **Cost (cons):** needs a small classifier change, not just data — `classify_change` /
  `window_events` must recognize `TCTK` / "Điều chỉnh mã" rows as code-only (append to
  `gso_codes`, emit no lineage event) — **with a test asserting no such row also carries a
  name/type/parent change**, so it's a deliberate skip, not a silent drop. (My scan: ghi_chu
  is uniformly "Điều chỉnh mã", so the risk is low but must be asserted.) The exact 2015-08-31
  code-change date won't carry a citation — acceptable; `gso_codes` records code+date anyway.
- **Alternative (rejected):** treat it as a citeable event — but there's no statement to
  reference, the công văn URL is unobtainable, and it would inject a non-legal internal
  dispatch into a decree/resolution corpus.
