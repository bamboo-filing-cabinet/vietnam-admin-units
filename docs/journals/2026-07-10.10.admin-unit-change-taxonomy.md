# Taxonomy of administrative-unit changes

Written 2026-07-10. A reference catalogue of the ways an administrative unit can
change over time, to ground the lineage model (relation vocabulary + Wikidata
property choices + `Ghi Chú` parsing). Extends the 7 change types first sketched
in discussion. Grounded in the GSO/NSO data (`2026-07-10.02`–`.09`) and Wikidata
modeling.

## Two levels: atomic changes vs named events

Most real events are **bundles** of atomic changes. Model the atoms; name the
bundles for communication and for matching the `Ghi Chú` vocabulary.

**Atomic change axes** (each event touches one or more):

| Axis | Values | Wikidata carrier |
| --- | --- | --- |
| **Existence** | create / dissolve / persist | P571 / P576 |
| **Territory** | gain / lose / none | area P2046; membership of sub-units |
| **Identity** | rename / retype / recode / none | label+P1448 / P31 / code prop |
| **Hierarchy** | re-parent / tier-change / none | P131 (time-qualified) |

**Identity outcome** (the decision that matters for us, per `.08`): does the
entity **continue (SAME)**, **end (END)**, or is a **new entity created (NEW)**?
Our rule: rename/retype/recode/re-parent/boundary-adjust → **SAME**;
merger/split/consolidation/reform → **new entities + lineage**.

### Merge family (many → one) — the key ambiguity

| # | Event | VI term | Identity | Wikidata | Example |
| --- | --- | --- | --- | --- | --- |
| M1 | **Absorption** — unit A absorbs B…; **A persists** (expanded), B… end | sáp nhập B vào A | A **SAME**, B… **END** | B P576 + **P7888 merged into** A; A area↑ | Hà Tây → Hà Nội (2008); Bắc Kạn → Thái Nguyên (2025, name+code survive) |
| M2 | **Consolidation / amalgamation** — A,B… combine into a **new** W; all cease | hợp nhất … thành … mới | A,B… **END**, W **NEW** | A,B P576 + P1366→W; W P571 + P1365→A,B | Yên Bái + Lào Cai → Lào Cai (`.09`) |

> **The M1/M2 ambiguity is the core modeling call.** The 2025 reform is *worded*
> as M2 ("…thành tỉnh mới có tên gọi là…"), yet GSO also designates a **primary
> survivor** via the structured `Tỉnh ĐC`/`Xã ĐC` link (e.g. old Lào Cai `10` →
> new `15`), which reads like M1. And Wikidata's community created **new items**
> (`.08`), i.e. M2. **Our decision (`.08`, DESIGN.md): treat every reform merge
> as M2 (new entity + lineage), and record the "primary/renamed-from" survivor
> and whole/partial shares as qualifiers** — so M1's continuity signal is not
> lost, just demoted to a qualifier.

## Modifiers (attach to an event, not events themselves)

- **Whole vs partial** — a merge/split/transfer can involve the whole unit or
  just part of it. `Ghi Chú` marks partial with **"một phần / 1 phần"** (404
  ward rows, `.06`). WD: **P518 applies to part** / **P1107 proportion** on the
  lineage statement.
- **Effective date + legal instrument** — every event carries a Nghị quyết +
  effective date (`P585`/`P580` qualifier; `P248 stated in` reference).
- **Primary-successor designation** — in a merge, GSO flags one predecessor as
  the code-inheriting / "đổi tên từ" primary (structured link); the rest are
  absorbed. A qualifier on the lineage edge, not a separate event.

## Mapping the original 7

1 → **E1** · 2 → **S1/S2** · 3 → **I1** · 4 → **T1** · 5 → **M1** (whole) or
**T1** (partial) · 6 → **T2 / S1** · 7 → **E2**. Added by recon: **M2**
(consolidate-to-new, distinct from M1 absorb), **I2** type change, **I3**
recode, **H1** re-parent, **H2** tier abolition, **H3** tier/type introduction,
**X1–X4** edge cases, and the whole/partial + primary-successor modifiers.

## How this feeds the model

Our lineage `relation` vocabulary is the merge/split/identity subset that crosses
an entity boundary:

- `replaces` / `replaced_by` (M2, S2) — new↔old, with whole/partial + primary +
  decree qualifiers.
- `merged_into` (M1, M2) — absorbed/consolidated predecessor → successor.
- `separated_from` (S1) — carve-out child → parent.
- `different_from` (X2) — the reuse/disambiguation guard.

SAME-entity events (I1/I2/I3/H1/T1–T3) are **not** lineage edges — they are
**time-qualified attribute changes on one entity** (name/type/code/parent/area),
i.e. `observations` rows, not new nodes. That split (edges vs attribute-history)
is the crux the taxonomy makes precise.
