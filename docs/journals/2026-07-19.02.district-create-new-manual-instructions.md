# Manual creation of the 5 Tier-C former-district items (maintainer procedure)

Written 2026-07-19. Decision context: [`2026-07-19.01`](2026-07-19.01.district-reconciliation-successor-tail.md)
Tier C. Those 4 districts (+ a revised Phú Quí) have **no former-district item on
Wikidata** — only their 2025 successor unit (đặc khu / phường) exists. Our model treats
the 2025 reform as a **universal abolition**: the former district *ends* (`P576 = 2025-07-01`)
and the đặc-khu/phường is a **new, commune-tier** entity — a different entity, not a retype.
So we **create a dedicated former-district item** for each, carrying its own end + a succession
link to the successor, making Tier C uniform with Tier A/B.

**Chosen path: the maintainer creates these 5 by hand** (only 5; avoids building a one-off
QuickStatements `CREATE` code path in `emit.py`; each item is reviewed before it lands, under
the maintainer's own WD account). This file is that procedure. After creation, the 5 flow back
into the normal pipeline as ordinary `verified` matches.

## Pre-flight — re-confirm no former item exists (avoid a duplicate)

Verified 2026-07-19 that WD has **no** former huyện/thị xã item for any of these — only the
successor. Re-confirm right before creating (search each name; you should see only the successor
đặc-khu/phường + unrelated items, e.g. for Hoàng Sa the *archipelago* Q274388 / an island):

```sh
for q in "huyện Hoàng Sa" "huyện Lý Sơn" "huyện Cát Hải" "thị xã Quảng Trị" "huyện Phú Quí"; do
  echo "=== $q ==="
  curl -s -G "https://www.wikidata.org/w/api.php" \
    --data-urlencode "action=wbsearchentities" --data-urlencode "search=$q" \
    --data-urlencode "language=vi" --data-urlencode "type=item" \
    --data-urlencode "limit=8" --data-urlencode "format=json" \
    -H "User-Agent: bamboo-filing-cabinet/1.0 (viett@appcard.com)" \
    | python3 -c "import json,sys; [print(r['id'],'|',r.get('label',''),'|',r.get('description','')) for r in json.load(sys.stdin)['search']]"
done
```

## Option B — manual UI (if you prefer clicking each)

Per item: **Create a new Item** → set the vi/en label + description from the table → add
`P31` (type), `P17 = Q881`, `P131` (parent), each with reference *stated in (S854) = NSO URL* →
add `P576 = 1 July 2025` with reference S854 = the abolition-law URL → add `P1366` (replaced by)
= successor with qualifier `P585 = 1 July 2025` + the law reference. Then open the **successor**
item and add `P1365` (replaces) = your new item, same P585 + law reference.

## After creation — hand the QIDs back

1. Note the 5 new QIDs QuickStatements assigns (the batch page lists each `CREATE`'s result).
2. Edit `mappings/districts-qid.csv` — set each of the 5 rows to `<newQID>,existing,verified`
   (`d-498/536/317/462-base` + `d-602-base`). This turns them into ordinary matches; the normal
   emitter then references them like any other district.
   - ⚠ The items now already carry the statements above. When you regenerate `na-districts.qs`,
     the emitter will *restate* `P131`/`P576` for them (`P571` is skipped — no `valid_from`; `P31`
     is skipped — single type span). QuickStatements treats identical statements as no-ops, so this
     is harmless. If you'd rather emit nothing for them, leave the 5 as `gap` — the manual items
     already stand on their own. **Recommended: set `verified`** so the audit sees them reconciled.
3. Re-run the pipeline + gates:
   ```sh
   uv run python -c "from vn_admin_units.cli import build_districts_all; build_districts_all()"
   uv run python -m vn_admin_units.reconcile --audit        # district audit (audit_district_qids)
   uv run python -m vn_admin_units.constraints              # D10 gate
   ```
   Expect the audit clean except the **accepted** cross-tier `TYPE` flags (Tier B/C context); the
   11-district tail is now fully resolved (0 `gap`).
4. Upload the regenerated `statements/na-districts.qs` (manual, personal WD account).
