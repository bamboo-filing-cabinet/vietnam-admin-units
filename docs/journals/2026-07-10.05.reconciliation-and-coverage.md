# Reconciliation keys + Wikidata coverage

Written 2026-07-10. Probes the reconciliation-facing questions raised after the
crosswalk probe (`2026-07-10.04`): name ambiguity, cross-tier integrity, P31
stability over time, and how much of the gazetteer already exists on Wikidata.

## #2 Reconciliation key: name + province is unique (current era)

National current ward dump (3,321 wards):

- 3,009 distinct names; **236 names are shared** across provinces (most-shared:
  `Xã Tân Tiến` ×7, `Xã Tân Thành` ×7, `Xã Tân An` ×6, `Xã Bình An` ×5).
- **But `(province, name)` collisions = 0.** Within any province, no two current
  wards share a name.

So the reconciliation key is **`name-fold + province`** — unique at the current
ward level with no coordinates needed. Bare name alone is not (312 wards would
be ambiguous); province disambiguates all of them.

Caveat: this is the **current** (2-level) era. The **pre-reform** era had a
district tier and duplicate commune names *within* a province across different
districts, so matching old items needs `name + district + province`. And
matching current→old is **many-to-one** (merges) — a lineage mapping (from the
crosswalk), not a 1:1 reconciliation.

## #5 Cross-tier integrity: clean

Every one of the 3,321 wards has a `MaTinh` that resolves to a province in the
same-date province dump (0 orphans, 34 provinces). The SOAP hierarchy is
internally consistent; a pipeline integrity check on this should always pass
(and flag loudly if it ever doesn't).

## #4 P31 is stable per (code, era)

Hà Nội wards across a post-reform window (`01/08/2025` → now): **0** wards kept
the same code **and** name but changed `LoaiHinh`. So a unit does not silently
change type in place; type changes (`Xã`→`Phường`, `Tỉnh`→`Thành phố`) arrive
bundled with a merge/rename/reform event (as with province `46` Huế and `75`
Đồng Nai — both changed name/era, not a silent in-place flip). Practical
consequence: `P31` can be set per `(code, era)` record without needing a
mid-life time-qualifier on a single item.

## #3 Wikidata coverage — WD holds the OLD structure

Instance counts on Wikidata (via WDQS):

| WD type | count |
| --- | --- |
| commune of Vietnam (`Q2389082`) | **9,925** |
| ward of Vietnam (`Q687188`) | **1,729** |
| đặc khu / special zone (`Q134999516`) | **6** |
| (communes located in a VN province) | 9,595 |

Total ward/commune-level items ≈ **11,654** — which tracks the **pre-reform**
(~10k commune) structure, **not** the current 3,321 units. Wikidata is a
snapshot of the *old* hierarchy (confirming the "mid-migration" state the
`vietnam-elections-wikidata` lao-cai files describe). Implications for the
"fix Wikidata" half of the project, now quantified:

- **Current units (3,321):** reconcile each to its best existing WD item by
  `name + province` (+ lineage), then **fix** it — `P31` (many still say
  "commune" where now `Phường`), `P131` (stale, pointing at abolished parents),
  and add `P571`/`P576`/`P7888` which VN admin items currently lack (`.03`).
- **Stale old items (~8k):** the abolished communes need `P576` (dissolved) +
  `merged into` / `replaced by` lineage — a large upstream cleanup, driven from
  our crosswalk-derived edges.
- **Gaps to create:** đặc khu is **6 on WD vs 13 in GSO → 7 missing**; plus new
  merged wards with no clean predecessor item.
- Because current→old is many-to-one, this is **not** a tidy 1:1 reconciliation;
  the crosswalk (`.04`) is what maps and justifies each edit.

## #6 English names — not in SOAP

Confirmed: `DMDVHC.asmx` returns Vietnamese only (no English field in any tier).
English labels for Wikidata must come from the Lịch Sử / crosswalk English-name
column (browser-only, per `.01`) or from existing WD items / transliteration.
Low priority — most existing WD items already carry English labels.
