# Phase 3 ward SOAP source rescue

## Status

Phase 3 is **blocked on authoritative ward membership snapshots** as of
2026-08-27. The NSO administrative-unit hostname returned DNS `SERVFAIL` during
the source-coverage audit, and the repository does not contain the ward SOAP
payloads needed to continue offline.

This is an availability observation, not a claim that NSO has permanently
retired the service. The rescue workflow below is prepared so a short recovery
window can be used immediately and safely.

## What the audit found

- `data/raw/soap/` has 28 `DanhMucTinh` province payloads and **zero** real
  `DanhMucPhuongXa` ward payloads.
- Git history contains no deleted or earlier ward SOAP cache.
- `tests/fixtures/danhmucphuongxa_sample.xml` is a three-row parser fixture with
  a deliberately stale `diffgr:before` row. It is not source data.
- Five `data/raw/crosswalk/ward_*.xls` files are preserved with manifest hashes:
  2017→2018, 2019→2020, 2024→2025, the 2025-07-01 reform boundary, and the flat
  2002→2025 code map. They are the representative spike sample, not the full
  event sweep.
- The crosswalk's fixed 13-column export drops `MaQuanHuyen` / district names.
  That parent context is present in `DanhMucPhuongXa` and is required to resolve
  duplicated pre-reform ward names named without codes in `Ghi Chú`.
- The cached `NghiDinh.aspx` index remains sufficient to prepare a high-recall
  date inventory offline: 544 legal records, including the 2026 Đồng Nai event.

Therefore the crosswalk and legal index preserve lineage evidence, but they do
not preserve the authoritative point-in-time roster that anchors ward identity.
The real ward graph must not be assembled by silently substituting Wikidata or
a third-party dataset for the missing SOAP layer.

## Rescue workflow added

`python -m vn_admin_units.ward_rescue` now:

1. fetches exact `DanhMucPhuongXa` response bytes through the canonical SOAP
   request path;
2. validates that the response parses into a non-empty ward roster before it is
   accepted;
3. stores `data/raw/soap/DanhMucPhuongXa_YYYY-MM-DD.xml` through `save_raw`;
4. records URL, method, ordered parameters, retrieval timestamp, byte count,
   SHA-256, row count, distinct ward codes, duplicate-row count, and acquisition
   reasons in `data/raw/manifest.jsonl`;
5. verifies both size and SHA-256 before treating an existing payload as
   complete;
6. skips verified dates on rerun, retries transient failures with exponential
   backoff, and stops after the first exhausted date by default so an unavailable
   source is not hammered; and
7. supports `--limit` for short recovery windows and repeatable `--date` for
   surgical acquisition.

The SOAP transport now exposes `fetch_units_raw`, returning response bytes
without a decode/re-encode round trip. Existing parsed callers retain their
original behavior through `soap_call`.

## Acquisition order

The default scope contains five dates, in recovery priority order:

1. `30/06/2025` — pre-reform roster (~10k wards) and the critical old
   ward→district map;
2. `01/07/2025` — post-reform roster (expected 3,321 wards);
3. `29/04/2026` — immediately before the known Đồng Nai event;
4. `30/04/2026` — the event's effective-date roster; and
5. the run date — freshness/current roster.

Commands:

```sh
uv run python -m vn_admin_units.ward_rescue --dry-run
uv run python -m vn_admin_units.ward_rescue
```

The `history` scope is deliberately **high recall**. It combines source-floor /
code-transition anchors, annual `01/01` audit anchors, and the day before + day
of every ward-relevant effective date found by a broad legal-title filter. On
2026-08-27 this produces **371 unique dates**, with the five critical dates
first. False-positive dates cost storage; a false negative could lose the only
authoritative observation around an event, so the rescue filter intentionally
errs wide.

```sh
uv run python -m vn_admin_units.ward_rescue --scope history --dry-run
uv run python -m vn_admin_units.ward_rescue --scope history --limit 20
uv run python -m vn_admin_units.ward_rescue --scope history
```

## Storage gate before the full history crawl

Do **not** blindly run and commit all 371 snapshots. A national ward response may
be several megabytes; the uncompressed working tree could reach gigabytes even
if Git delta-compresses similar snapshots efficiently.

After the five critical files are recovered:

1. record their exact compressed and uncompressed sizes;
2. estimate the 371-date working-tree and packed-Git cost;
3. decide between raw `.xml`, deterministic lossless compression, Git LFS, or a
   dedicated archival repository while preserving the response SHA-256 and
   reproducible retrieval metadata; and
4. run the history scope in reviewed batches (`--limit N`), committing each
   verified batch only after the manifest/coverage gate passes.

The current tool writes exact `.xml` response bytes. Changing the storage form
is a separate explicit decision; never discard or reserialize source content to
save space.
