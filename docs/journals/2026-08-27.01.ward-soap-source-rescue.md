## What the audit found

  `DanhMucPhuongXa` ward payloads.
- Git history contains no deleted or earlier ward SOAP cache.

- Five `data/raw/crosswalk/ward_*.xls` files are preserved with manifest hashes:
  2017→2018, 2019→2020, 2024→2025, the 2025-07-01 reform boundary, and the flat
  2002→2025 code map. They are the representative spike sample, not the full
  event sweep.
- The crosswalk's fixed 13-column export drops `MaQuanHuyen` / district names.
  That parent context is present in `DanhMucPhuongXa` and is required to resolve
  duplicated pre-reform ward names named without codes in `Ghi Chú`.
- The cached `NghiDinh.aspx` index remains sufficient to prepare a high-recall
  date inventory offline: 544 legal records, including the 2026 Đồng Nai event.

Therefore the crosswalk and legal index preserve lineage evidence, but they do
not preserve the authoritative point-in-time roster that anchors ward identity.
The real ward graph must not be assembled by silently substituting Wikidata or
a third-party dataset for the missing SOAP layer.

## Rescue workflow added

`python -m vn_admin_units.ward_rescue` now:

1. fetches exact `DanhMucPhuongXa` response bytes through the canonical SOAP
   request path;
2. validates that the response parses into a non-empty ward roster before it is
   accepted;
3. stores `data/raw/soap/DanhMucPhuongXa_YYYY-MM-DD.xml` through `save_raw`;
4. records URL, method, ordered parameters, retrieval timestamp, byte count,
   SHA-256, row count, distinct ward codes, duplicate-row count, and acquisition
   reasons in `data/raw/manifest.jsonl`;
5. verifies both size and SHA-256 before treating an existing payload as
   complete;
6. skips verified dates on rerun, retries transient failures with exponential
   backoff, and stops after the first exhausted date by default so an unavailable
   source is not hammered; and
7. supports `--limit` for short recovery windows and repeatable `--date` for
   surgical acquisition.

The SOAP transport now exposes `fetch_units_raw`, returning response bytes
without a decode/re-encode round trip. Existing parsed callers retain their
original behavior through `soap_call`.

Commands:


The default `history` scope combines source-floor / code-transition anchors,
annual `01/01` audit anchors, and each distinct ward-affecting effective date.
The classifier recognizes explicit `cấp xã`, standalone `xã`, `phường`, `thị
trấn`, and `đặc khu` mentions while excluding district-only `thị xã` titles.
Ward parent transfers remain relevant even if no ward identity changes.

On 2026-08-27 the 544-record legal cache contains 453 matching instruments on
179 distinct effective dates from 2005 onward. Those dates, 25 distinct
source/annual anchors, and five critical/current dates produce **204 unique
snapshot dates** after five overlaps. The critical dates remain first.

An explicit `history-bracketed` scope adds the day before every effective date
and produces **369 unique dates**. It is retained as an emergency diagnostic
ceiling for a suspected incomplete or ambiguous legal index; it is no longer
the normal history plan. Consecutive effective-date snapshots already provide
the prior observed state for later events, while annual anchors independently
check for unindexed changes.

```sh

uv run python -m vn_admin_units.ward_rescue --scope history --limit 20
uv run python -m vn_admin_units.ward_rescue --scope history
uv run python -m vn_admin_units.ward_rescue --scope history-bracketed --dry-run
```

## Storage gate before the full history crawl

Do **not** blindly run and commit all 204 snapshots. A national ward response may
be several megabytes; the uncompressed working tree could reach gigabytes even
if Git delta-compresses similar snapshots efficiently.

After the five critical files are recovered:

1. record their exact compressed and uncompressed sizes;
2. estimate the 204-date working-tree and packed-Git cost;
3. decide between raw `.xml`, deterministic lossless compression, Git LFS, or a
   dedicated archival repository while preserving the response SHA-256 and
   reproducible retrieval metadata; and
4. run the history scope in reviewed batches (`--limit N`), committing each
   verified batch only after the manifest/coverage gate passes.

The current tool writes exact `.xml` response bytes. Changing the storage form
is a separate explicit decision; never discard or reserialize source content to
save space.

Key checks:

- `2025-07-01` and `2026-04-29` are byte-identical: no intervening roster
  change.
- `2026-04-30` and `2026-08-27` are byte-identical: the current roster is the
  effective-date roster.
- The April 30 event creates/removes no ward codes. Exactly ten Đồng Nai rows
  keep their code and parent but change `TenPhuongXa` + `LoaiHinh` from

- The 2025 crosswalk has 10,040 raw base rows but 10,035 distinct base codes;
  the SOAP roster's 10,035 unique wards confirms that the crosswalk's five
  blank-base creations are not missing pre-reform roster members.
- Critical working-tree size is 6.5 MiB. `gzip -9 -c` totals approximately
  398 KiB (about 5.8% of raw), so deterministic lossless compression is the

  33–39 MiB as individual gzip payloads. This is a conservative ceiling because
  later 3,321-row rosters are substantially smaller.

The original critical-source blocker is resolved and the 2025 ward slice is now

## Planning refinement — 371 explained and reduced

The initial 371-date number was not 371 known changes. It was a safety envelope:
180 dates from the broad title filter, 180 corresponding day-before dates, 22
annual anchors, four source anchors, and five critical/current dates, reduced by
overlaps. Review made two corrections:

- standalone ward-tier matching removes district-only `thị xã` false positives,
  leaving 453 instruments on 179 distinct effective dates; and
- blanket day-before snapshots are redundant because the previous retained
  observation supplies the before-state of the next event.

The resulting acquisition contract is 179 event dates + 25 distinct anchors +
five critical/current dates - five overlaps = **204 unique dates**. The old
fully bracketed behavior remains reproducible as `history-bracketed` (369 dates)
rather than disappearing from the audit trail.
