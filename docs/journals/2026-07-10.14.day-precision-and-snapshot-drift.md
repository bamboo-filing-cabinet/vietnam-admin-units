# Day-level change dates + a counting pitfall (NO drift)

Written 2026-07-10. Answers "can we get exact day-level change dates?" — yes.
**Correction:** an earlier version of this journal claimed the SOAP service
"drifts" (returns different counts for the same date over time). **That was
wrong** — it was my own measurement inconsistency plus duplicate rows in the
source. Corrected below. The service is stable.

## Yes: day-level precision is available (two ways)

1. **SOAP `DenNgay` is day-precise and bisectable.** Bisecting the national ward
   count pinned the 2019-wave drop to exactly **2020-01-01**. Earlier bisects
   nailed 2008-08-01, 2025-07-01, 2004-06-30, 2002-01-01, 2026-04-30.
2. **Lịch Sử change-log gives the effective date + decree directly** per unit.

A single year has **multiple distinct change days** (monthly 2019 stepped down
in ~Mar, ~Jun, ~Nov, Dec, 2020-01-01). Admin changes are day-level by decree —
no sub-day granularity exists or is needed.

**Preferred source for dating: Lịch Sử** (decree-linked, authoritative), with
SOAP diffs as a detector/cross-check. Reinforces the hybrid decision (`.11`).

## The "drift" was a counting pitfall — retracted

I saw the same date report different ward counts across runs (11,164 vs 11,181
for 2019-01-01) and wrongly concluded upstream drift. The real causes, found
with the canonical fetch tool (`vn_admin_units.fetch`, added because of exactly
this):

1. **Two different counting methods across throwaway scripts.** `.13` counted
   **distinct codes** (a dict keyed by `MaPhuongXa`); later probes counted **raw
   `<MaPhuongXa>` tags**. Those differ whenever a snapshot has duplicate rows.
2. **Historical snapshots contain exact-duplicate rows.** Canonical counts:

   | date | rows | distinct codes | duplicate rows |
   | --- | --- | --- | --- |
   | 2019-01-01 | 11,181 | 11,164 | **17** |
   | 2020-01-01 | 10,797 | 10,778 | **19** |
   | 30/06/2025 | 10,035 | 10,035 | **0** |

   The duplicates are **exact repeats** (same code *and* name, e.g. `07684 Xã
   Lão Hộ` twice), clustered in one district's contiguous code range — a GSO
   export artifact, not two wards colliding. `MaPhuongXa` is still semantically
   unique per real ward (consistent with `.05` A2, which sampled current data).

**Determinism confirmed:** 4 immediate repeats of each date were identical, and
the difference was fully explained by (raw − distinct) = duplicate-row count. No
temporal drift.

## Consequences (updated)

- **No drift ⇒ no re-verification churn.** SOAP historical snapshots are stable.
- **Ingest must dedupe exact-duplicate rows** at the ward tier (dedupe on the
  full row / `(MaTinh, MaQuanHuyen, MaPhuongXa)` within a snapshot). Concrete
  instance of the DESIGN "data-quality normalization" task; log what's dropped.
- **Count distinct codes, via the canonical tool** — never raw tags, never
  ad-hoc scripts. `uv run python -m vn_admin_units.fetch --tier ward --date …`
  reports rows/distinct/duplicates consistently.
- The verbatim-raw + `manifest.jsonl` provenance decision still stands on its own
  merits (reproducibility, licensing) — **not** justified by "drift" (there is
  none).
- `.12`/`.13` exact counts: the *distinct*-code figures (dict-based) are the
  right ones; raw-tag figures are inflated by duplicate rows. Patterns hold
  either way.

## Process lesson

The phantom "drift" came from re-implementing the fetch+count in each throwaway
script with subtle differences. Fix: the reusable `vn_admin_units.fetch` tool +
`soap.parse_rows` — one canonical, DocumentElement-scoped path. Use it.
