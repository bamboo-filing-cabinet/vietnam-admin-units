# Reconciliation audit caught a mis-match (Cà Mau province vs city)

Written 2026-07-11. Before treating the province batch as upload-ready, ran a
correctness audit of the reconciled QIDs (`reconcile --audit`). It found — and I
fixed — one wrong QID that would have corrupted Wikidata.

## What the audit checks

`audit_province_qids`: (offline) completeness, pre-QID distinctness, post⊆pre;
(online) **name-aware instance-of** — every `Tỉnh …` row must map to a
`province`-type item, every `Thành phố …` to a `city`-type item.

## The bug: Cà Mau matched the capital city, not the province

`wd_lookup("Cà Mau")` returned, first, **Q25262 = Cà Mau *city*** (the provincial
capital), which is in Vietnam (P17=Q881), so the `P17=Vietnam`-only filter
accepted it. The correct item is **Q33354 = Cà Mau *province***. Search returned
both (plus a rural district and an airport); nothing but the type disambiguates
them, and P17 alone doesn't.

Impact if uncaught: the batch would have **dissolved the province into the city**
and **merged Bạc Liêu into Cà Mau city** — nonsense on Wikidata. This is exactly
the failure a pre-upload audit exists to catch.

## Fix + a second catch

- Fixed pre `Tỉnh Cà Mau` (code 96) → **Q33354**, `match_status=manual`.
- Re-audit then flagged a **POST-NOT-IN-PRE** issue: `build_all` reads post QIDs
  straight from the CSV (doesn't re-derive), so the *post* Cà Mau row still held
  the stale Q25262. Fixed post row → Q33354 too. Re-audit: **issues=0**.
- Rebuilt: `Q25262` gone from the batch; Bạc Liêu (Q36658) now correctly
  dissolves/merges into Cà Mau (Q33354). Final batch: 116 statements, 29
  dissolutions, 0 self-refs, 0 P571, all referenced.

## Lessons (carry to Phase 2 ward reconciliation)

1. **`wd_search` + P17=Vietnam does not disambiguate type.** Same-named
   city/province/district all pass. The **name-aware instance-of audit is a
   required gate**, not optional — never treat a reconciled batch as ready
   without `--audit` green.
2. **Manual fixes are `match_status=manual`** so resume/rebuild keep them.
3. **Post QIDs live in the CSV** (read by `build_all`, not re-derived), so a
   pre-row fix needs the matching post-row fix — the audit's POST-NOT-IN-PRE
   check catches the inconsistency. (Possible Phase-2 cleanup: derive post QIDs
   from lineage at build time instead of storing them, removing this footgun.)
4. Wards will have far more of this (thousands, heavier name collisions) — the
   audit + manual-residue loop is the model; budget for it.

## Follow-up: strengthened the audit (type was not enough)

The type-only check proves each QID is *a* province/city, not the *right* one. So
added an independent **label-match**: the item's own vi/en label must match the
GSO province name (diacritic-folded, so GSO `Hoà Bình` == Wikidata `Hòa Bình` —
old vs new tone-mark placement). Re-audit of all 63: every label matches its name
(the lone flag was that Hoà/Hòa diacritic variant — a false positive, fixed by
folding). Combined gate now = completeness + distinctness + post⊆pre + type +
label. `issues=0`. This closes the "wrong entity of the right type" gap for
provinces; residual same-name/same-type/different-*era* risk is covered here by
label-match + these being the well-known modern provinces (all typed `province`/
`former provinces`/`city` of Vietnam, labels exact).
