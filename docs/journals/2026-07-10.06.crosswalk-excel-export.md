# Crosswalk Excel export — schema + how lineage is (and isn't) encoded

Written 2026-07-10. Follows `2026-07-10.04` (crosswalk page) and `.05`. Two real
Excel exports were downloaded from `Doi_Chieu_Moi.aspx` and parsed (workspace
`.venv`: pandas + xlrd). This nails the export schema and — importantly — how
merges/splits are represented, which reshapes the ingest design.

Files (in `~/Downloads`, `.xls` = real OLE/BIFF, read with `xlrd`):
- `… cấp Xã _ 10_07_2026 và 31_07_2025 .xls` — 2.4 MB, base = current.
- `… cấp Xã _ 30_06_2025 và 10_07_2026 .xls` — 4.2 MB, base = pre-reform.

## Export schema (fixed, 13 columns)

`Tỉnh · Tên Tỉnh · Xã · Tên Xã · Nghị định · Ngày hiệu lực` (base) ·
`Tên Xã DC · Xã DC · Nghị định.1 · Ngày hiệu lực.1 · Tên Tỉnh DC · Tỉnh DC`
(comparison) · `Ghi Chú`.

- **The export drops the district (QH / Tên QH) columns** shown in the on-screen
  grid, even when base is pre-reform. District hierarchy must come from **SOAP**
  (`DanhMucQuanHuyen`), not this export.
- Codes are zero-padded strings; dates parse as real datetimes (`Ngày hiệu lực`
  values seen: `2025-07-01` and `2026-04-30` — the reform + the Đồng Nai upgrade).
- `Nghị định` is per-unit: **35 distinct provincial resolutions** in the current
  export (e.g. `1656/1664/1676/1685/1686/NQ-UBTVQH15`, all 16/06/2025).

## The key finding: structured columns = PRIMARY 1:1 only

Base = pre-reform export (`30/06/2025` → current), 10,040 old wards:

- **3,321** old wards carry a structured `Xã DC` (new-ward) link;
  **3,306 of them keep the same code** — the new ward inherits its
  *renamed-from* primary predecessor's code (e.g. old `00004` Phường Trúc Bạch →
  new `00004` Phường Ba Đình).
- **6,719** old wards have **blank `Xã DC`** — they were absorbed as
  **non-primary** constituents (confirmed: Phường Quán Thánh, which the new
  Ba Đình's notes list as merged-in, has blank `Xã DC`).
- Grouping new wards by `Xã DC`: **fan-in max = 1** — i.e. the structured link
  never expresses many-to-one. **Merges are not in the columns.**

So the crosswalk's *columns* give only the primary rename/successor edge
(old-primary → new, usually same code). The **full many-to-one merge membership
and the "một phần / 1 phần" split contributions live ONLY in the `Ghi Chú`
prose.**

## Where the narrative lives (directionality matters)

- **base = new** export: `Ghi Chú` populated for **all 3,321** new wards, each a
  full composition, e.g. *"Đổi tên từ phường Trúc Bạch thành phường Ba Đình,
  hợp nhất phường Quán Thánh, phường Trúc Bạch, một phần phường Cửa Nam … Bỏ cấp
  huyện"*. `Bỏ cấp huyện` on 3,320/3,321. This is the rich lineage source.
- **base = old** export: `Ghi Chú` mostly **blank** (5,384/10,040), verbs skew to
  `thành lập` (511), `hợp nhất` (306), `Đổi tên` (236), `phần` (143), no `Bỏ cấp
  huyện`. Sparser — use it for the structured primary link + code inheritance,
  not the narrative.

## Consequence for ingest (updates `.04`)

Building **complete** lineage edges needs three inputs, not one:

1. **Primary successor + code inheritance** — base=old export, `Xã DC` column
   (3,321 edges, 3,306 same-code).
2. **Full merge/split membership** — parse the **base=new** export's `Ghi Chú`
   Vietnamese prose: `Đổi tên từ A thành B` → primary rename; `hợp nhất X, Y` →
   merged constituents; `một phần / 1 phần Z` → partial (split) contribution.
3. **Absorbed old wards (6,719)** — destination only via the new ward's `Ghi
   Chú` (name match), since their `Xã DC` is blank.

So `Ghi Chú` parsing (or snapshot-diff cross-check) is **required** for a
complete edge set — the export is not a clean relational many-to-many table.
Fallback if prose parsing proves unreliable: primary-link (structured) +
SOAP snapshot-diff to detect the absorbed set, with `Ghi Chú` kept as a
human-readable reference on each new unit.

## Other observations

- **New units with no old counterpart: 5** blank-base rows — đặc khu Bạch Long
  Vĩ, Cồn Cỏ, **Hoàng Sa** (`20333`), Lý Sơn, Côn Đảo. (Others like Vân Đồn /
  Cô Tô existed pre-reform as districts, so they have an old counterpart.)
- **Đặc khu count wobble:** 12 in the base=new export vs 13 in the raw SOAP dump
  (`.03`) — reconcile during ingest (likely a naming/threshold edge case).
- Pre-reform commune-level total = **10,040** (at 30/06/2025), consistent with
  Wikidata's ~10k commune items (`.05`) — WD mirrors the old structure.

## Practicalities confirmed

- Excel export **works and is public** (no login); Chrome's "ask where to save"
  means each export needs a manual confirm — fine interactively, but for
  automated ingest prefer **replaying the export POST** (viewstate) or the
  DevExpress callback.
- `xlrd` reads these `.xls` fine despite a "file size not multiple of sector
  size" warning (harmless).
- Raw exports currently only in `~/Downloads`; the ingest build should commit a
  cache (converted to CSV/parquet for diffability) for reproducibility.
